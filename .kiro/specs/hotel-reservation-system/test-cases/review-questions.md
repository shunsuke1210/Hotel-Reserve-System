照らした仕様書：requirements.md、design.md、design-screens.md、brief.md、context.md（根拠の確認のために research.md の ADR と future-improvements.md も見た）。テストケースのファイルは変更していない。

**まとめ**
- 重複：66組。削除または統合を提案するケースは 73件（01：11件、02：12件、03：8件、04：2件、05：5件、06：35件）

- 判断が必要な論点：高 14件、中 16件、低 23件

## 1. 重複の指摘

**重複とした基準**
- 同じ前提・同じ操作・同じ期待結果を確かめているもの。予約の番号や金額などのデータが違っても、確かめる規則・操作・期待結果が同じなら重複とした
- 次のものは重複に数えていない
  - 層が違うだけのもの（関数の単体の確認と API の確認、API と画面、06 の画面テスト）。例：TC-PR-117〜122（PriceCalculator）と TC-RS-084・085・088・089（見積もり API）、TC-PR-047〜050（暦の関数）と TC-CH-078〜080（キャンセルの API）、TC-PR-150（検索 API）と TC-RS-097・098（G02 の表示）、TC-PR-114・115 と TC-RS-079・080、TC-IT-058〜063（画面テスト）
  - 1回の実行の結果を項目ごとに分けたもの（例：TC-PR-057〜059、TC-PR-101〜106、TC-CH-147・148）。確かめる項目が違うため
  - Web とフロントで同じ規則が働くことを確かめるもの（要件 5.4・7.3・8.1 の「同じ規則を適用する」。例：TC-CH-005、TC-CH-040、TC-RS-205〜209）

**残す側の決め方**
1. 期待結果がより具体的な側（金額・宛先・明細・在庫まで確かめる側）を残す
2. 同じくらいなら、その受け入れ基準を担当しているファイル（網羅表に載せている側）を残す。権限（2.2・2.4）と他人のデータ（1.10）は 02 を残す
3. 06 は「機能ごとのケースでは確かめにくい、複数の機能や時間をまたぐ動き」を確かめる方針（06 の冒頭）なので、1つの操作だけで 01〜05 と同じことを確かめるケースは 06 から外す。06 の 2.1 を状態の移り方の一覧として残したい場合は、ケースの代わりに 01〜05 のケース ID を並べた表にする
- 削除したケースを網羅表に載せていた場合は、残したケースの ID（別のファイルのものを含む）に書き換える

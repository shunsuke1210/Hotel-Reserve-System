# テストケース：空室検索・予約の作成・名簿・フロントの予約登録

対象の仕様：`requirements.md`・`design.md`・`design-screens.md`・`brief.md`・`context.md`・`traceability.md`（いずれも 2026-10-21 時点。実装前のレビューの決定 DT-M17〜DT-M47・L-24〜L-46 を反映済み）。実装はまだないため、仕様書から期待結果を決めている。

担当範囲：要件 3.1〜3.6、4.1〜4.25、5.1〜5.6、7.1、7.20、9.1、9.5、10.8、10.9、13.2、13.5（在庫に戻る日）、14.1〜14.5、14.7。
範囲外（別の担当）：料金の金額の計算式、予約の変更・キャンセル・ノーショー、部屋の選び方の細部（階の均等・同じ階）、チェックイン以降のフロント業務、メールの言語、暦の関数の細かい境界。

## 1. テスト観点

### 正常
- ログインしていない訪問者が空室を検索でき、全日程を通して同じ部屋が空いている客室タイプが「空室あり」になる
- 同じ客室タイプで複数室を予約でき、人数は予約全体で区分ごとに入力する
- 予約の入力画面に会員情報が自動で入り、同行者・到着予定時刻・宿泊者（代表者）・「現地で入力」を扱える
- 朝食（区分ごとの人数・全泊）と時間外（部屋ごと、初期値は全室同じ）を選べる
- 支払い方法（事前決済・現地払い）を選べ、早期割の対象では事前決済で早期割が付く
- 最終確認の画面で宿泊約款とキャンセル規定を表示し、同意すると部屋を15分間確保する
- 事前決済は時間外を除く全額を決済して確定し、現地払いは登録カードをカード保証にして確定する
- 確定で予約番号を発行し、予約完了のメール（事前決済は入金完了のメールも別に）を作る
- フロントが会員を検索して予約者に指定し、Web と同じ条件で予約を登録・確定する。当日に時間外を追加できる
- 宿泊客とフロントが名簿を入力でき、子ども・幼児も記録し、追加した項目も扱える
- 予約の入力で入れた同行者の連絡先に予約者の連絡先が自動で入り、後から名簿の画面で変えられる
- 会員が自分の予約の一覧と詳細（明細・支払い済みの額・返金額・現地で払う額）を見られる。決済待ちの予約は「お支払い待ち（残り○分）」として表示し、期限切れの予約は表示しない

### 異常
- 未ログインで予約に進む、違う客室タイプの混在、定員の超過、室数が大人の人数を超える
- 日付の不正（過去日・365日より先・当日 25:00 以降・泊数0・不正な日付）と、人数・室数の不正
- 約款に同意しない、決済待ちの予約がある会員の新しい確保
- 決済の拒否・決済サービスの障害（障害のときの決済の記録は PENDING のまま照合を待つ）、時間切れの後の確定
- 別の画面ですでに確定した予約の確定（ALREADY_CONFIRMED）、確定の処理の途中の障害（INTERNAL。決済の後の失敗は返金して取り消す）
- 満室・連泊できない在庫なし・確保の直前に満室になった場合
- 会員でない人の予約のフロント登録、清掃員によるフロントの操作、他人の予約・名簿の参照
- 時間外・朝食・到着予定時刻の範囲外の値、名簿の必須項目の不足、名簿の形式の誤り（旅券番号の文字種）

### 境界
- 365日の上限（到着 2027-11-09／11-10／11-11、連泊で最後の夜がまたぐ場合、365泊／366泊）
- 当日の締め切り（23:59／翌 00:59／01:00／01:01）、到着日が今日と昨日
- 泊数0・大人0・室数0・子ども −1・幼児 −1
- 空室検索の回数制限（同じ IP から直近60秒に60回／61回、1回目の要求から59秒・60秒での解除）
- 定員（1室で大人2〜5、2室で大人6と7、デラックス キングの大人2と3）と室数（大人の人数と同じ／1つ多い）
- 早期割の期限の日とその前日（到着 2027-02-10／02-09）
- 時間外の時刻（アーリー 11／12／14／15、レイト 12／13／15／16）、到着予定時刻（14:30／15:00／25:00）、朝食の人数（各区分の人数と同じ／1つ多い）
- 確保の期限（確保 10:00 に対し 10:14／10:15／10:16）
- 確保から確定までの間の条件の変化（当日予約の締め切りの前 00:59／ちょうど 01:00:00／後 01:02 の確定、早期割の期限をまたぐ確定、割増の登録で額が変わる／変わらない）
- 全日程空いている部屋の数と室数（1室と2室）、各夜の空室の数（お知らせを作る／作らない）
- 故障中の終了予定日の前日・当日・翌日
- 名簿の行数（宿泊人数より1少ない／同じ／区分の超過）
- 一意制約の違反のやり直しの回数（4回／5回／6回）

### 連携
- 確保（HOLD）と空室検索・ほかの会員の確保（期限内は埋まり、期限切れは空き。期限切れで時間切れの処理の前の確保がある部屋も確保できる）
- 同じ最後の1室の同時確保、同時確保のやり直し、Web とフロントの同時の予約
- 確定と決済代行（模擬）・明細・メールの作成、時間外の料金の現地精算、決済サービスの障害で PENDING のまま残る決済と警告の一覧の「決済の照合待ち」
- 別の idempotencyKey の確定の同時の送信（2つのタブ）、フロントの登録の同じ idempotencyKey の再送（二重に予約・決済しない）
- 連泊できない在庫なしのお知らせ（検索・Web の確保・フロントの登録から作る、重複のまとめ、故障中の期間が原因の場合）
- 故障中の期間と在庫（終了予定日の翌日から戻る、部屋の状態に関係なく日付で判定）
- フロントの登録と Web の見積もりの料金の一致、予約の作成と名簿

### 状態遷移
- 決済待ち（PENDING_PAYMENT）→ 確定（CONFIRMED）：room_nights が HOLD から BOOKED へ
- 決済待ち → 時間切れ（EXPIRED）：確保の解除、時間切れのメール、定時処理の再実行で重複しない
- 時間切れの予約への確定、決済の拒否・障害の後も決済待ちのまま → 期限内の再試行で確定
- 確保の後に料金が変わった確定（PRICE_CHANGED）→ 新しい料金の確認 → もう一度の確定
- 決済待ちの解消（確定・時間切れ）の後に新しい確保ができる
- 確定済みの予約への新しい idempotencyKey での確定（ALREADY_CONFIRMED で、決済しない）
- 5室の予約の団体の判定（確保の時点では is_group＝false・max_room_count＝0、確定で true・5）
- フロントの事前決済の登録で決済が断られた予約 → 期限切れ（EXPIRED）：部屋の解放と、断られた決済の記録（FAILED）
- お知らせの解決の後に、同じ条件で新しいお知らせができる
- 名簿の未完了 → 完了

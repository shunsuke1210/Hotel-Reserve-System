# Implementation Plan

各タスクは、設計書（design.md・design-screens.md。テスト設計で決めた細部は design.md の「設計の補足」）の内容を実装する。テストはそのタスクの中で一緒に書き、テスト名に受け入れ基準の ID（例：`[6.19]`）を入れる（traceability.md と照合するため）。日付と時刻はすべて日本時間の時計を通して扱う。

- [x] 1. 基盤：開発環境・データベース・API と画面の土台
- [x] 1.1 リポジトリと開発ツールを整え、API の契約の共通部分を作る
  - 宿泊客アプリ・フロントアプリ・清掃アプリ・API・共有の契約パッケージの5つを、1つのリポジトリで管理できるようにする
  - 型の検査、整形、単体テストの仕組みを全パッケージで使えるようにする
  - 契約パッケージに、列挙（予約の状態・部屋の状態・役割・年齢区分・言語・支払い方法など）とエラーの形・エラーコードの一覧を定める
  - 完了状態：リポジトリの最上位から、全パッケージの型の検査とテストを1回の操作で実行でき、すべて成功する
  - _Requirements: 1.10, 2.4_

- [x] 1.2 開発用のデータベースと環境設定を用意する
  - PostgreSQL 17 を1回の操作で起動できるようにし、接続先や秘密の値を環境ごとの設定ファイルから読み込む
  - 結合テスト用のデータベースを、開発用とは別に用意する
  - 完了状態：1回の操作で開発用とテスト用のデータベースが起動し、設定ファイルの接続先で接続できる
  - _Requirements: 9.1_

- [x] 1.3 API を公開用と社内用の2つの待ち受け口で起動し、共通の仕組みを入れる
  - 1つのプロセスで、公開用（宿泊客向け）と社内用（スタッフ向け）の2つの待ち受け口を立て、それぞれに別の機能群を載せられるようにする
  - 業務エラーを契約のエラーの形に変換する仕組み、要求ごとのログ（個人情報を出さない）、日本時間に固定した時計（テストで時刻を差し替えられる）を入れる
  - 完了状態：2つの待ち受け口がそれぞれ稼働確認の応答を返し、公開用の待ち受け口では社内用の稼働確認の URL が「見つからない」になり、テストで時計を任意の時刻に固定できる
  - _Requirements: 2.2, 2.4, 3.6_

- [x] 1.4 データベースのスキーマと、結合テストの仕組みを作る
  - design.md の Physical Data Model のすべてのテーブルを作る
  - 部屋×宿泊日の一意制約、メール・電話番号の有効な会員の間での一意、会員ごとの決済待ちは1件まで、お知らせの未解決の重複のまとめ、を制約で保証する
  - 操作履歴は追記だけにし、更新・削除をデータベースが拒否するようにする
  - 結合テストのたびに、スキーマを適用した空のテスト用データベースを用意する仕組みを作る
  - 完了状態：スキーマの適用が成功し、同じ部屋・同じ宿泊日の2行目の追加と、操作履歴の更新が、結合テストでどちらもデータベースに拒否される
  - _Requirements: 1.3, 4.18, 9.1, 10.9, 18.2_

- [x] 1.5 初期データを用意する

  - 振込先（銀行名・支店・口座種別・口座番号・名義）をホテルの設定として登録する

- [x] 1.6 3つの画面アプリの土台を作る

  - 宿泊客アプリに5言語の切り替えの仕組みを入れ、日付・数字を言語ごとの書き方で、時刻を日本時間で表示する共通部品を作る。画面の切り替えの定義と文言ファイルは、機能（検索・認証・予約・マイページ）ごとに分けておき、後のタスクが別々のファイルを編集できるようにする
  - スタッフ向けの2つのアプリは日本語だけにする
  - 完了状態：3つのアプリがそれぞれ起動して空のトップ画面を表示し、宿泊客アプリでは言語を切り替えると見出しの文言が変わる

- [x] 1.7 外部サービスのインターフェースと模擬実装を作る
  - 決済（カードの登録・決済・返金・カードの削除）、機械翻訳、メール送信のインターフェースを定め、業務のコードはインターフェースだけを使うようにする
  - 模擬の決済は、カード番号の末尾で成功・拒否・一時的な障害を返し、同じ冪等キーの決済を二重に行わない。カード番号は保存しない
  - 模擬の翻訳は言語名を付けた文を返し、模擬のメールは送信の記録を残す
  - 完了状態：模擬の決済の単体テストで、末尾0002のカードが拒否され、同じ冪等キーで2回決済しても1回分しか記録されない

- [x] 2. 業務ルールの関数（フレームワークとデータベースに依存しない）
- [x] 2.1 (P) 暦のルールを作る
  - 営業日（1:00 が日の境目）、暦の日付、その夜の割増（金・土・祝前日と特定期間のうち高いほう）、早期割の期限（暦の3か月前の同じ日、なければ月末）、無料キャンセルの期限（到着日15:00の48時間前）を求める
  - 完了状態：0:59 は前日・1:00 は当日、5/31 到着の期限が 2/28（うるう年は 2/29）、振替休日の前日が割増の対象、になることを単体テストで確認できる
  - _Requirements: 3.5, 3.6, 6.6, 6.7, 6.8, 6.12, 8.3_
  - _Boundary: BusinessCalendar_

- [x] 2.2 (P) 料金の計算を作る
  - 夜ごと・年齢区分ごとの税込み単価（率の合算と −50% の下限、整数の計算、100円未満の切り捨て）、判定人数による人数割、連泊割、早期割を計算する
  - 区分ごとの朝食の人数（全泊に同じ人数）、部屋ごとの時間外（常に現地精算）、夜ごと・人ごとの宿泊税（5,000円未満は0円）の明細を作る
  - 完了状態：要件の計算例で、大人21,500円・子ども10,700円・宿泊税を除く合計61,900円・宿泊税600円になり、判定人数（2名1室→2、10名10室→0、10名5室→10）と宿泊税の境目（4,999／5,000／19,999／20,000円）の単体テストが通る
  - 時間外の料金は、入力で渡された「選んだ時点の料金の版」で計算する。後から加えた人・朝食も、入力で渡された「加えた時点の版」で計算する
  - _Requirements: 4.10, 6.1, 6.2, 6.4, 6.5, 6.9, 6.10, 6.11, 6.13, 6.14, 6.15, 6.16, 6.19, 11.5_
  - _Boundary: PriceCalculator_

- [x] 2.3 キャンセル料と宿泊税の返金のルールを作る
  - 個人（期限内は0円、期限後は取り消した部屋・人の最初の夜）、団体（30日前・7日前・前日の各 0:00 を境に20%・50%・100%）、早期割（返金しない）、早期チェックアウト（残りの夜の部分キャンセル）を判定する
  - 宿泊料金が一部でも返金される夜の宿泊税は全額返金し、返金されない夜の宿泊税はキャンセル料・ノーショー料と同じ区分に付け替える
  - 料金の明細の型を使うので、2.2 の後に行う
  - 完了状態：design.md の P-06 の宿泊税の例（5つ）と、各段階の境目のちょうどの時刻の単体テストが通る
  - 返金しないのは早期割を適用した夜だけとし、早期割なしの料金で加えた夜は個人・団体の規定で計算する
  - 早期割で返金しないのは宿泊料金と宿泊税だけとし、朝食は返金する
  - 客室タイプを移した夜は、タイプ変更の差額（下位への移動の返金分、有償の上位の追加分）を含めた額を「1泊分」と団体の基準額に使う。団体のノーショーは全泊の100%とする
  - 日程の変更で取り消すもとの夜の規定（個人の期限・団体の段階）は、もとの到着日を基準に判定する
  - _Requirements: 7.6, 7.7, 8.4, 8.5, 8.6, 8.9, 8.10, 8.19, 20.7, 8.25_
  - _Boundary: CancellationPolicy_

- [x] 2.4 (P) 部屋の選び方を作る
  - 1室は「割り当て済みが最も少ない階 → 上の階 → 番号の小さい順」、2室以上は「同じ階で番号の範囲が最も狭い組み合わせ」で選ぶ
  - 同じ階に収まらない場合は使う階の数が最も少ない組み合わせを選び、配置上どの階にも収まらないかどうかも返す
  - 完了状態：同点の階の扱い、同じ階への2室以上の割り当て、配置上収まらない場合の判定の単体テストが通る
  - _Requirements: 9.2, 9.3, 9.4_
  - _Boundary: RoomSelector_

- [x] 2.5 (P) 部屋の状態のルールを作る
  - 12の状態を、空室の清掃グループ・連泊グループ・その他の3つに分ける
  - 清掃員に許すのは、空室の清掃グループの中の変更、連泊グループの中の変更、「来客なし→清掃完了」だけとする。「その他」のグループの中の変更（例：故障中→チェックイン済み）とグループをまたぐ変更は許さない。フロント以上はすべての変更を許す
  - 完了状態：役割ごと・状態の組み合わせごとに、許可・拒否が設計の P-12 の表のとおりになる単体テストが通る
  - _Requirements: 12.1, 12.2, 12.3, 12.4, 12.7_
  - _Boundary: RoomStatusRules_

- [x] 2.6 (P) 団体の判定を作る
  - 予約期間中の最大室数が5以上なら団体とし、同じ会員の夜が重なる予約の室数を夜ごとに足して、最大が5以上ならすべてを団体にする
  - 完了状態：室数を5から4に減らしても団体のまま、3室＋2室の重なる予約が両方とも団体になる、の単体テストが通る
  - _Requirements: 8.7, 8.8_
  - _Boundary: GroupEvaluator_

- [ ] 3. 共通のサービス
- [x] 3.1 セッションと認証・権限の共通部品を作る

  - 会員用・スタッフ用の認証の確認、役割の判定（管理者＞フロント＞清掃員）、他サイトからの要求の拒否（独自のヘッダー）、ログインの回数制限、パスワードのハッシュ化を入れる
  - 公開用の待ち受け口はスタッフのセッションを受け付けない
  - 公開用 API の要求の言語を決め（Accept-Language、ログイン中は会員の preferred_locale）、ApiError の message をその言語で作る仕組みを入れる（design.md L-11。1.3 の実装で担当が決まっていないことが分かったため、ここに加えた）。要求のログの userType に MEMBER・STAFF を入れる
  - 完了状態：清掃員のセッションでフロント以上の操作を呼ぶと「権限がない」、管理者だけの操作をフロントが呼ぶと「権限がない」になる結合テストが通る

- [x] 3.2 定時処理の土台を作る
  - 定時処理を日本時間の時刻で登録し、多重起動を防ぎ、開始・終了・結果を記録する
  - どの処理も、何度実行しても結果が同じになる作りを前提として、対象の選び方と記録の共通の仕組みを用意する
  - 完了状態：テスト用の処理を2つの実行で同時に起動しても1回だけ実行され、実行の記録が1件残る

- [x] 3.3 (P) 操作履歴の記録を作る

  - 完了状態：スタッフの更新の操作の後に操作履歴が1件増え、その履歴を変更しようとするとデータベースが拒否する
  - 操作の内容には、氏名・住所・連絡先・旅券番号などの個人情報の値を書かず、項目の名前と対象の ID だけを記録する
  - 1つの操作（API の1回の要求）につき1行を記録し、同時に変わる部屋の状態は内容に含める
  - _Requirements: 18.1, 18.2, 18.3_
  - _Boundary: AuditLogService_

- [ ] 3.4 (P) メールの作成と送信を作る

  - 開発環境だけで、作成したメールの一覧を社内用 API で見られるようにする（画面のテストで確認のリンクを取り出すため）
  - 完了状態：英語を選んだ会員への予約完了のメールが英語で作られ、同意を取り消した会員には定期配信のメールが作られず、開発用の一覧にメールが表示される結合テストが通る
  - 未回収の支払いのお願いのメール（振込先と金額）のテンプレートを用意する

- [ ] 3.5 (P) 客室・約款の内容と翻訳文を提供する

  - 初期データの投入のときに翻訳文を作って保存する
  - 完了状態：言語を指定して客室タイプの一覧と宿泊約款を取得すると、その言語の翻訳文が返る

- [ ] 3.6 (P) お知らせの記録と、清掃時間の判定を作る
  - お知らせを種類・対象・期間とともに作り、同じ重複のまとめのキーの未解決のお知らせがあれば作らない。解決済みにする操作と、未解決の件数・一覧の取得を用意する
  - 部屋と日付を指定すると、その日の前の客のチェックアウト時刻（既定12:00、レイトならその時刻）から次の客のチェックイン時刻（既定15:00、アーリーならその時刻）までが2時間未満かを判定し、そうならお知らせを作る判定の処理を用意する（ちょうど2時間は作らない）。この処理は、予約・変更・時間外・移動・入れ替えの各タスクから呼ぶ
  - 完了状態：同じ客室タイプ・同じ日程のお知らせを2回作ろうとしても未解決は1件のままで、清掃時間の判定が設計の例（12:00→15:00 なし、12:00→14:00 なし、12:00→13:00 あり、14:00→15:00 あり、15:00→13:00 あり）のとおりになる

  - 業務の操作（チェックイン・チェックアウト・故障中の設定と終了・定時処理）からの変更を受け付ける入口を用意し、後のタスクはこの入口だけを使う
  - 完了状態：清掃員の役割で「その他」グループの中の変更を求めると断られ、業務の操作からの「清掃完了→チェックイン済み」は記録つきで反映される結合テストが通る

- [ ] 4. 会員とスタッフの認証・会員情報の API
- [ ] 4.1 スタッフのログイン API を作る
  - スタッフ番号とパスワードでログインし、役割を返す。ログアウトと本人情報の取得を用意する
  - 初期データとして、管理者・フロント・清掃員の各役割のスタッフを、3.1 のハッシュ化でパスワードを作って登録する
  - 完了状態：正しい番号とパスワードで役割つきのセッションができ、誤りでは「ID またはパスワードが違う」になり、短時間に繰り返すと制限される
  - スタッフを停止する内部の関数（停止と同時にセッションを消す）と、それを呼ぶ開発者用のスクリプトを用意する

- [ ] 4.2 会員登録 API を作る
  - 必須項目（カードを含む）と、日本に住所がない外国人の国籍・旅券番号を検証し、カードを模擬の決済に登録して識別子・ブランド・下4桁だけを保存する
  - メールアドレス・電話番号が有効な会員と重複していれば断る（確認の期限が切れた申込は、登録の前に削除して重複に数えない）。配信の同意（初期は同意しない）を日時と方法とともに記録する
  - 確認メールを作り、確認が終わるまで会員として利用できない状態にする
  - 完了状態：登録の後に確認メールが送信待ちに入り、確認前はログインできず、同じメールアドレスでの2回目の登録が断られる結合テストが通る

- [ ] 4.3 会員のログイン・メール確認・パスワード再設定の API を作る
  - メールアドレスの確認（24時間で期限切れ）、ログイン、ログアウト、パスワード再設定の申込（登録の有無にかかわらず同じ応答）と再設定（1時間で期限切れ）を用意する

# Research & Design Decisions

## Summary
- **Feature**: `hotel-reservation-system`
- **Discovery Scope**: New Feature（新規開発。既存のコードはない）
- **Key Findings**:
  - 要件の「1人あたりの料金」「客室タイプごとの基本料金」「予約全体の人数」「違うタイプの混在」は同時に満たせない。ユーザーの判断で「1予約＝1客室タイプ」に変更した（ADR-08）
  - 二重割り当ての防止は、「部屋×宿泊日」に一意制約を持つ占有テーブルで、データベースが保証する形にするのが最も単純で確実（ADR-06）
  - 宿泊客向けの画面は外部に公開し、スタッフ向けは社内に限定する。そのため API を2つの待ち受け口に分け、公開側には宿泊客向けの機能だけを載せる（ADR-03）

## Research Log

### 技術のバージョン
- **Context**: 技術スタックの確定（React＋NestJS、PostgreSQL）
- **Sources Consulted**: [InfoQ: NestJS 12 roadmap](https://infoq.com/news/2026/04/nestjs-12-roadmap-esm)、[Prisma: Supported databases](https://www.prisma.io/docs/orm/v7/reference/supported-databases)、[TanStack Query](https://upd.dev/TanStack/query/src/tag/v5.73.2/packages/react-query)、[React 19 + Vite + React Router v7 の構成例](https://dev.to/molly_1024/the-ultimate-react-19-vite-tailwind-css-v4-shadcn-ui-react-router-v7-starter-template-113p)
- **Findings**:
  - NestJS は 11 系が安定版。12 系（ESM への移行など）が準備中だが、出荷状況は確認できなかった
  - Prisma ORM は v7 の文書で PostgreSQL 18 までを対応一覧に載せている
  - React 19、Vite 7 以降、React Router 7、TanStack Query 5 の組み合わせが2026年時点で一般的
- **Implications**: 各ライブラリは主バージョンだけを固定し、細かい版は導入時に最新の安定版を確認する。NestJS は 11 系で始める（12 系への移行は今後の判断）

### 日本の祝日
- **Context**: 祝前日の割増（要件 6.6）には、振替休日を含む祝日の一覧が必要
- **Sources Consulted**: [npm holiday-jp](https://npmjs.com/package/holiday-jp)
- **Findings**: npm のライブラリは更新状況や振替休日への対応を確認できなかった
- **Implications**: ライブラリは使わず、内閣府が公開している「国民の祝日」の一覧（振替休日を含む）を祝日テーブルに取り込む。年1回、データを更新する運用とする（ADR-10）

### 金沢市の宿泊税
- **Sources Consulted**: [金沢市：宿泊税について](https://www4.city.kanazawa.lg.jp/soshikikarasagasu/shiminzeika/gyomuannai/1/4/28700.html)、[金沢市宿泊税条例](https://www.city.kanazawa.ishikawa.jp/reiki/reiki_honbun/a400RG00001719.html)
- **Findings**: 2024年10月1日の宿泊分から、5,000円未満は課税しない。5,000円以上20,000円未満は200円、20,000円以上は500円。判定に使うのは税抜の素泊まり料金。年齢による免除はない
- **Implications**: 税額の区分を料金設定の版に持たせる。初期値は上記のとおり

### 特定電子メール法
- **Sources Consulted**: [総務省パンフレット](https://www.soumu.go.jp/main_sosiki/joho_tsusin/d_syohi/pdf/m_mail_pamphlet.pdf)
- **Findings**: 同意した相手にだけ送ること、同意の記録を残すこと、送信者名と受信拒否の方法を表示すること、拒否された後は送らないことが求められる
- **Implications**: 同意の履歴テーブル（marketing_consents）を設け、配信メールの定型文に送信者名と受信拒否の方法を必ず入れる

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| モジュール分割の単一 API（採用） | NestJS の1つのコードベースを業務ごとのモジュールに分け、計算ロジックはフレームワークから独立した関数にする | 構成が単純。料金・キャンセル料などの計算を単体でテストしやすい | モジュール間の依存を設計で縛る必要がある | 依存の向きを design.md で固定する |
| マイクロサービス | 予約・清掃・会員などを別サービスにする | 独立して配置・拡張できる | 1施設・学習用には過剰。予約と在庫の整合が分散トランザクションになる | 不採用 |
| フロントと API を一体化（Next.js） | 画面とサーバーを1つにする | 型の共有が容易 | ユーザーが「画面とサーバーの分離」を選んだ | 不採用 |

## Design Decisions

各決定は Class A（取り消しにくい：データ構造、API の契約、認証、画面をまたぐ構成）と Class B（命名・内部構造・テスト設計など、実装者の裁量）に分ける。

### ADR-01（Class A）: 3つの画面アプリと1つの API
- **Context**: ユーザーは React＋NestJS（画面とサーバーの分離）を選び、「フロント画面・清掃員画面・客の予約画面の3つが必要」と述べた
- **Alternatives Considered**: ① 3つの画面アプリ ② スタッフ用を1つにまとめた2つの画面アプリ
- **Selected Approach**: 宿泊客アプリ（guest-web）、フロントアプリ（front-web）、清掃アプリ（cleaning-web）の3つの React アプリと、NestJS の API を1つのリポジトリ（pnpm workspaces）で管理する。後のフェーズの管理者メニューはフロントアプリに追加する（管理者はフロントの上位の役割のため）
- **Rationale**: 利用者・端末・公開範囲がそれぞれ違う。清掃アプリはタブレット向けの画面にでき、宿泊客アプリだけを外部に公開できる
- **Trade-offs**: ビルドの設定が3つになる。ログインなどの共通部品は、各アプリで小さく持つ
- **Follow-up**: 確認状況：ユーザーが選択・発言済み

### ADR-02（Class B）: ORM に Prisma を使う
- **Selected Approach**: スキーマの定義とマイグレーションに Prisma ORM を使う。在庫の確保など、一意制約や行ロックが必要な箇所はトランザクションの中で処理する
- **Rationale**: 型付きのデータアクセスと、マイグレーションの管理を1つの道具で賄える

### ADR-03（Class A）: 公開範囲で API の待ち受け口を分ける
- **Context**: ユーザーは「宿泊客向けの画面は外部公開を前提にし、スタッフ向けは社内に限定する」を選んだ
- **Alternatives Considered**: ① 1つの待ち受け口で、リバースプロキシのパスで制限する ② 1つのプロセスで2つの待ち受け口（公開用・社内用）を立て、それぞれに別のモジュール群を載せる
- **Selected Approach**: ②。公開用（GuestApp、ポート3001）には宿泊客向けのコントローラーだけを、社内用（StaffApp、ポート3002）にはスタッフ向けのコントローラーと定時処理を載せる。リバースプロキシ（nginx）は外部向けに guest-web と公開用 API だけを、社内向けに front-web・cleaning-web と社内用 API を中継する
- **Rationale**: 公開側のプロセスにスタッフ向けの機能がそもそも存在しないため、設定の誤りでスタッフ向けの機能が外部に漏れることがない
- **Follow-up**: 確認状況：ユーザーが選択済み。TLS 証明書と外部公開の手続きは運用の範囲

### ADR-04（Class A）: サーバー側セッションによる認証
- **Selected Approach**: ログインに成功したら、セッションをデータベースに保存し、ブラウザには推測できない ID だけを Cookie（HttpOnly・Secure・SameSite）で渡す。会員とスタッフは別の種類のセッションにし、公開用 API はスタッフのセッションを受け付けない。パスワードは Argon2id でハッシュ化する
- **Rationale**: 退会・アカウント停止・削除のときに、セッションを消せばすぐにログインを無効にできる（要件 1.11、19.4）
- **Follow-up**: 確認状況：ユーザーが選択済み

### ADR-05（Class A）: 外部サービスは差し替えられる模擬実装にする
- **Selected Approach**: 決済（PaymentGateway）、機械翻訳（Translator）、メール送信（MailSender）をインターフェースとして定義し、MVP では模擬実装を使う。模擬の決済は、カード番号の末尾で成功・失敗を切り替えられる。カード番号そのものは保存せず、模擬の決済が発行する識別子（トークン）、ブランド、下4桁、有効期限だけを保存する
- **Rationale**: 費用がかからず、決済の失敗などの例外も自由にテストできる。本物のサービスには、インターフェースの実装を差し替えるだけで移れる
- **Follow-up**: 確認状況：ユーザーが選択済み

### ADR-06（Class A）: 部屋×宿泊日の占有テーブルで二重割り当てを防ぐ
- **Context**: 要件 3.2・9.1・9.5 は「全日程を通して同じ部屋が空いていること」を求め、同時に予約されても二重に割り当ててはならない
- **Alternatives Considered**: ① 予約の期間（開始日・終了日）が重ならないことを、アプリで確認する ② 「部屋×宿泊日」1行の占有テーブルに一意制約をかける ③ PostgreSQL の排他制約（期間の重なり）を使う
- **Selected Approach**: ②。room_nights テーブルに（room_id, stay_date）の一意制約を持たせ、決済待ちの確保と確定済みの割り当ての両方を行として入れる。同時に同じ部屋を取ろうとすると、片方が一意制約の違反になり、次の候補の部屋を試す
- **Rationale**: 判定が単純で、データベースが確実に保証する。夜ごとの空き状況の集計（お知らせ、要件 10.8）にも、そのまま使える
- **Trade-offs**: 長期滞在では行数が増える（253室×365日で約9万行が上限で、問題にならない）
- **Follow-up**: 確認状況：設計書でユーザーに提示し、設計の承認で確認する

### ADR-07（Class A）: 料金は夜ごとの控え（スナップショット）と明細で管理する
- **Context**: もとの部分は予約時の料金を保ち、追加分は変更時点の料金で計算する（要件 7.4）。人数割・連泊割は、最終的な人数・泊数の段階で、**各夜のもとの料金表の率**を使って適用し直す（2026-10-16 ユーザー回答）
- **Selected Approach**: 料金設定を「版」（rate_versions）として持ち、予約した夜ごとに、適用した版・基本料金・割増率・早期割の対象かどうかを控えとして保存する（stay_night_prices）。請求額は「明細」（charge_lines）として保存し、変更のたびに古い明細を取り消し扱いにして、新しい明細を作る。入金と返金は payments に記録し、残高は「有効な明細の合計 − 入金 ＋ 返金」で求める
- **Rationale**: 後から料金表が変わっても、どの夜をどの条件で計算したかを再現できる。明細の履歴が残るので、売上の集計（後のフェーズ）にもそのまま使える
- **Follow-up**: 確認状況：率の扱いはユーザーが選択済み。テーブル構造は設計の承認で確認する

### ADR-08（Class A）: 1つの予約は1つの客室タイプ
- **Context**: 設計中に、要件の組み合わせでは混在する予約の料金を決められないことが分かった
- **Selected Approach**: 1つの予約は1つの客室タイプだけとする（要件 4.2 を変更）。フロントが一部の部屋を別のタイプに移した場合は、予約の客室タイプは変えず、差額を調整の明細として追加する
- **Follow-up**: 確認状況：ユーザーが選択済み（「混在を認めない」）

### ADR-09（Class B）: 定時処理は社内用 API のプロセスで動かす
- **Selected Approach**: @nestjs/schedule で定時処理を登録し、PostgreSQL のアドバイザリーロックで多重起動を防ぐ。どの処理も何度実行しても結果が同じ（冪等）になるように作る。決済待ちの確保は、時間切れかどうかを読み取りのたびにも判定するので、処理が少し遅れても在庫の判定は正しい
- **Rationale**: 社内サーバー1台で動かすので、別の仕組み（キューなど）は不要

### ADR-10（Class B）: 日付と時刻の扱い
- **Selected Approach**: 宿泊日は日付型（DATE）、時刻は時間帯つきの時刻型（timestamptz）で保存する。「今日」「営業日」の判定は、日本時間に固定した時計（BusinessClock）を通して行い、テストでは時刻を差し替えられる。祝日は祝日テーブルから判定する
- **Rationale**: サーバーの設定に左右されず、境界の時刻（25:00、9:00、前日10:00 など）をテストで再現できる

### ADR-11（Class A）: 来館客の会員登録は、客自身の端末で行う
- **Context**: 要件 5.3 は「来館した客がその場で会員登録（カードを含む）を終えたら予約を登録できる」と定める。会員登録にはカード番号の入力が必要
- **Selected Approach**: 来館客は、自分のスマホ（またはロビーに置いた端末）で宿泊客アプリの会員登録を行う。フロントアプリには会員登録の画面を設けない
- **Rationale**: スタッフがカード番号を扱わないようにするため（要件定義の際に、電話でカード番号を聞く案を同じ理由で退けた）
- **Follow-up**: 確認状況：ユーザーが承認済み（2026-10-19）

### ADR-12（Class A）: 複数室の予約で一部の部屋のタイプを変えたときの差額
- **Context**: 下位タイプへの移動の返金（要件 9.10）と有償アップグレードの差額（要件 9.13）は、料金が1人あたりのため、その部屋に何人泊まるかが分からないと計算できない（予約全体の人数しか入力していない）
- **Selected Approach**: 2室以上の予約で一部の部屋のタイプを変えるときは、フロントがその部屋の人数（大人・子ども・幼児）を入力する。1室の予約では、予約の人数をそのまま使う
- **Follow-up**: 確認状況：ユーザーが承認済み（2026-10-19）

### ADR-13（Class A）: ノーショーの判定を延ばしたときの期限
- **Context**: 要件 8.15 は「フロントが判定を延ばせる」と定めるが、延ばした後にいつ判定するかが決まっていない
- **Selected Approach**: フロントは延ばすときに期限の時刻を選ぶ（最も遅くて、到着日の翌日のチェックアウト時刻12:00まで）。期限を過ぎてもチェックインしていなければ、15分ごとの定時処理でノーショーと判定する
- **Follow-up**: 確認状況：ユーザーが承認済み（2026-10-19）

### ADR-14（Class B）: 「お知らせ」と「警告」を分ける
- **Selected Approach**: 要件 10 のお知らせ（解決ボタンで消す・件数をバッジで表示）は notices テーブルに保存する。要件 9.16・13.3 の警告（故障中の部屋への割り当て、終了予定日を過ぎた故障中）と、要件 11.6 の要精算は、画面を開いたときにその場で計算し、予約状況チャートの横の「対応が必要な一覧」に表示する。状態が解消すれば自動で消える
- **Rationale**: 警告は状態そのものから決まるので、保存すると実際の状態とずれるおそれがある

### ADR-16（Class A）: 宿泊税は前払いに含め、宿泊料金が返金される夜だけ返金する
- **Context**: 事前決済には宿泊税も含まれる（要件 4.19 の「全額」）。キャンセルなどで返金するとき、宿泊税をどう扱うかが決まっていなかった
- **Alternatives Considered**: ① 泊まらなかった夜の宿泊税はすべて返金する ② 宿泊税は前払いに含めず、いつも現地で受け取る（自治体は徴収のしかたを事業者に任せており、予約サイトでもよく見る形） ③ 宿泊料金が返金される夜だけ、宿泊税も返金する
- **Selected Approach**: ③（2026-10-19 ユーザーが決定）。宿泊料金が一部でも返金される夜は、その夜の宿泊税を全額返金する。宿泊料金が返金されない夜（早期割、期限後のキャンセル料・ノーショー料の対象となる夜、団体の100%）は返金しない（要件 8.19）
- **Consequences**: 返金しない宿泊税は、宿泊が行われていないため市に納める対象にならない。ユーザーの判断（2026-10-19）により、宿泊料金の一部のように扱い、その夜の返金しない宿泊料金（キャンセル料・ノーショー料）と同じ区分の明細に付け替える（要件 20.7）
- **Follow-up**: 確認状況：ユーザーが決定済み（2026-10-19）

### ADR-15（Class B）: 早期割の追加分の判定
- **Selected Approach**: 予約に夜を追加するとき、早期割の条件（要件 6.12）は**予約の到着日**と**追加した日**で判定する。出発日を変えずに到着日の前に夜を足す変更も夜の追加として扱う（要件 7.17、2026-10-20 ユーザー決定）。夜を動かす日程変更は、要件 7.9 のとおり取消と追加として扱う
- **Rationale**: 要件 6.12 は「到着日」を基準に定めているため

### Generalization（設計の一般化）
- 予約の変更・部分キャンセル・ノーショー・早期チェックアウト・タイプの変更は、すべて「予約の内容が変わり、料金と明細を計算し直して、差額を精算する」という同じ処理として扱う（ReservationChangeEngine）。キャンセル料の計算（CancellationPolicy）と料金の計算（PriceCalculator）は、どれからも同じ関数を呼ぶ
- お知らせの3種類（連泊できない在庫なし・離れた部屋・清掃時間の不足）は、同じ notices テーブルと「重複をまとめるキー」で扱う

### Build vs. Adopt
- 採用：NestJS（API）、Prisma（データアクセス）、React・React Router・TanStack Query（画面）、react-i18next（多言語）、zod（入力の検証と型の共有）、Argon2（パスワード）、@nestjs/schedule（定時処理）、@nestjs/throttler（連続アクセスの制限）、date-fns と @date-fns/tz（日付）、Playwright（画面のテスト）、Vitest（単体テスト）
- 自作：料金計算・キャンセル料・部屋の割り当て・状態の移り方は業務ルールそのものなので、フレームワークから独立した関数として自作する
- 不採用：祝日のライブラリ（理由は上記）、ジョブキュー（不要）

### Simplification（簡素化）
- 共通の画面部品のパッケージは作らない（3つのアプリで共有するのは API の型だけ）
- 警告と要精算は保存せず、その場で計算する（ADR-14）
- 故障中の在庫の戻し（要件 13.2）は、日付の範囲で判定するので定時処理は不要

## Risks & Mitigations
- 同時予約による競合 — 一意制約と再試行で防ぐ。同じ部屋を同時に取り合うテストを用意する
- 料金計算の誤り — 要件の計算例（61,900円）と境界値を単体テストで固定する
- 公開側への攻撃（総当たりのログイン、大量の検索） — 待ち受け口の分離、連続アクセスの制限、入力の検証、セッションの Cookie の属性で防ぐ
- 定時処理の止まり・遅れ — 冪等にし、在庫の判定は時間切れを読み取り時にも確認する。処理の実行結果をログに残す
- 祝日データの更新漏れ — 翌年分がないときは起動時と毎月の処理で警告する
